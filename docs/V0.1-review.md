# CasioSync V0.1 R1 embedded reliability review

Independent source review completed on 13 October 2026, Brisbane time. This review covers the Casio-only fork and its new optional watch settings. It is a release review of bounded behavior and failure handling, not a physical watch test or a multi-year endurance claim.

## Scope and retained behavior

The firmware has no LF station encoders, carrier output, transmitter task/timers, transmission schedule or LF web endpoints. The retained Bluetooth code includes the user's working GW-BX5600 SP handshake, separate font and battery operations, four watch profiles, daily listening slots and Always Wait. The retained Wi-Fi code provides setup AP, checked credentials, a daily web-access schedule and bounded NTP wake/recovery exceptions. Listening and watch time use the same BT timezone and offset; Wi-Fi access uses its independent timezone.

The 122 exact advertised names are protocol candidates: one BX, 118 Standard and three experimental Analogue. The 119 BX/Standard optional-feature candidates derive from pinned upstream metadata, which includes generic defaults. Neither catalog membership nor a successful compilation establishes that an individual watch accepts every optional feature. Unknown names and the excluded continuous-connection/MIP generations cannot silently select a Standard fallback. An unnamed advertisement is eligible only for an already-bound BX address.

## Findings corrected before publication

1. The notification channel predicate initially routed the new alarm, timer and automatic-adjustment response headers to SP_DATA. Optional settings subscribe to TIME/all-features instead. The final predicate explicitly recognizes `0x13`, `0x15`, `0x16`, `0x18`, `0x11` and the separate battery header on the settings channel, while retaining SP response handling.
2. Optional feature application now checks the active profile before indexing profile arrays.
3. The watch-options checksum now copies the stored bytes with `memcpy` before clearing the checksum field, so structure padding is preserved instead of relying on a memberwise copy.
4. The Standard protocol comment now describes the actual 11-byte TIME command. The original 10-byte inherited form is not presented as the new encoder's format.
5. Optional-settings documentation now distinguishes an admission reserve from a guaranteed deadline. A stalled synchronous ATT operation can consume the reserve and fail the whole sync; the existing 45-second transaction deadline requests normal disconnect and safe cleanup. Optional work never manufactures a successful TIME result.
6. An inherited low-memory rollback weakness in the daily Wi-Fi access timezone handler was hardened. The previous zone is now kept in a fixed 32-byte buffer, and capacity for both apply and rollback is reserved before any live schedule setting changes. Allocation failure returns a controlled error with the previous settings intact.
7. The first C3 link exposed missing MCU-specific linker metadata in the inherited crash-dump gate library. Version 1.0.1 adds the `src/esp32c3` metadata marker and installs it alongside the classic ESP32 marker. The gate still builds from source; its panic-path C++ is unchanged. Final C3 ELF inspection must establish that the SDK panic writer reaches the wrapper, whose default-Off path skips flash writing.

## Memory, ownership and failure handling

New packet helpers inspect bounded names and stage at most 17 bytes. They allocate no heap, register no callbacks and create no tasks. Each merge validates packet shape and desired values before changing output, copies the actual watch reply, and alters only explicitly selected fields. Readback checks those selected fields; a transport acknowledgement alone is not reported as matching watch settings. Unsupported packet layouts and capabilities are refused.

Desired watch choices and status are bounded to four profiles. Feature results are literal status strings, and recent sync history is a fixed four-entry ring per profile. The watch-settings JSON handler accepts a bounded body, uses one fixed JSON document owned by the HTTP loop, requires complete typed/range-checked options and rejects updates during a watch transaction or pairing. Shared API serialization has a fixed capacity and returns a controlled error on overflow. Existing Arduino/NimBLE String/STL allocations remain, with heap admission checks before controller initialization and connection. This review found no newly unbounded collection or accumulating feature-history allocation.

Application settings, GATT operations and HTTP handlers share loop-task ownership. NimBLE callbacks publish fixed response/discovery buffers under critical sections and connection state through atomics. Client callbacks, host events and scan-control storage have retained lifetimes. The synchronous ATT callback's stack storage remains alive until completion or GAP cancellation; a local timeout does not abandon it. A host teardown barrier prevents characteristic-cache reuse while the previous connection is still active. Failed controller cleanup retains ownership and uses bounded recovery rather than deleting live callback storage. The progress monitor is fault recovery, not a periodic maintenance reboot.

The C3 SuperMini build explicitly selects GPIO8 with active-low output for its discrete blue LED. The Node32s uses GPIO2 active-high. Single-core targets use unpinned task creation; dual-core targets retain valid core assignments. Task creation is checked. Failure to create the progress monitor blocks Bluetooth startup, and LED-task failure leaves the initialized LED off. No guessed LF/peripheral pins are driven.

## Persistence and time

CasioSync uses its own config and status filenames and a separate CRC-protected settings schema, rather than interpreting the transmitter's settings. Required config mutations use a checked temporary write, byte readback and rename. The new watch-options file follows the same replacement pattern and restores previous RAM choices when saving fails. Options carry the bound watch address and protocol and are rejected for another binding. Corrupt options are ignored with defaults Off and no startup rewrite.

Optional watch preferences are written only on explicit UI Save. Feature results and battery samples remain in RAM. Runtime BT status retains the optional first-success-per-Brisbane-day snapshot policy, including the persisted daily quota; later events remain in RAM. A failed runtime snapshot is not repeatedly retried during the day. Debounced required config saves latch a storage fault after failure and stop automatic retries. Wi-Fi SDK credential persistence is disabled. Filesystem mount failure preserves existing flash and provides setup-AP recovery through an explicit erase action. Crash dumps remain default Off and write only when that setting is enabled and a panic occurs.

Elapsed/deadline comparisons use unsigned differences for short `millis()` intervals and 64-bit monotonic time for uptime, clock age and long-running retry schedules. Wall time is admitted through the retained strong SNTP hook; an untrusted clock blocks watch synchronization. These properties limit drift/rollover failure paths without introducing routine reboot requirements.

## Validation and limits

The focused test reviewer reported successful ASan/UBSan runs of the production feature executor/notification callback fixture and the existing production battery callback fixture. The new transport fixture checks all five optional headers on TIME/all-features, fragmented replies, wrong channels/headers, retained SP headers, binding/model/profile/range guards, read/merge/readback failures, unchanged values, time/font admission reserves and rollover. This is host fault evidence for the actual extracted code, not a real-watch transaction.

The release owner is responsible for recording the final focused fault checks, render review, Node32s/C3 compilations, image/partition checks and ELF validation against the exact published source. This independent reviewer did not run the full suite or an ESP32 compile. The full suite must run after source publication, following the user's release order; its actual result belongs in release evidence and notes.

Physical acceptance is still required for the new project's Wi-Fi/AP behavior, both board LEDs, scheduled watch requests and newly added optional settings. The inherited user's BX time-sync success is relevant evidence for that retained handshake, but does not validate every new watch model or preference. Multiple preference groups are separate transactions and can partially apply before a watch disconnects. Readback confirmation is stronger than delivery evidence, while the physical display remains unverified.

No unresolved source blocker was found in the reviewed feature integration after the corrections above. Release approval depends on the release owner's final build and focused-check evidence. Future device captures should be used to narrow each model's capabilities and validate its specific packet layouts; generic metadata must remain labeled experimental.
