# V0.1 R4 embedded reliability and browser review

Independent review on 13 October 2026, Brisbane time. The reviewer ran the focused browser group, inspected the final source/test delta, and edited only its browser failure diagnostics and this review document. The full suite and board compilation were not run by this reviewer.

## Corrections and production scope

R3's post-publication suite reached the battery transport fixture and stopped because it omitted the real remaining-transaction-time dependency. The corrected fixture extracts `btTransactionRemainingMs()` from production and marks the transaction active before the optional battery read. The focused test reviewer reported five battery cases, the optional-feature executor case and the model-catalog case passing under the sanitizer harness. Its new cases cover inactive transactions, the exact admission threshold, optional-read skipping while retaining the required TIME handshake, deadline abort and `millis()` rollover. Production Bluetooth code was not changed to satisfy the fixture.

The previously unreached browser group exposed an actual optional-control visibility bug. For the unsupported MTG-B3000 profile, all feature capabilities were false and the master row's `hidden` property was true, but its computed display remained `flex`. The existing author `.toggle-row` display rule overrode the browser's default handling of the HTML hidden attribute. This was a rendering defect, rather than an asynchronous test failure.

The release owner added the scoped rule `#watchFeaturesMasterRow[hidden],#watchFeaturesSave[hidden]{display:none}` and re-embedded the UI. It applies only when those optional controls are marked hidden and preserves the supported-profile controls and existing layout. The browser test retains actual visibility assertions; it was not weakened to check only the attribute. A diagnostic state snapshot was added to make future visibility failures distinguish capability selection from CSS behavior.

Beyond that scoped UI correction and R4 revision/changelog labels, production behavior is unchanged from R3. Companion headers, partition layout and dependency sources are unchanged. Watch packets, callback/task lifetimes, scheduling, Wi-Fi/NTP, config rollback and flash-write cadence remain covered by the [R1 reliability review](V0.1-review.md). The [R3 manifest enumeration review](V0.1-R3-review.md) also remains applicable. Removing historical compiled folders from main is packaging cleanup; immutable earlier tags retain those artifacts.

## Focused browser result

After the CSS correction, `node scripts/test-ui-browser.cjs` completed with exit code 0. One focused browser integration group passed. Its log is `/tmp/casiosync-r4-browser-focused.log`; the release owner should retain the log in release evidence. The run covered the seven-page sidebar, GitHub links, recurring BT slot/timezone edits, independent per-profile alarm drafts, successful saves, failed-save draft retention, actual hiding of unsupported optional controls, independent history/crash toggles, the overnight Wi-Fi schedule, h/m/s uptime and phone layout. No page errors were reported. Screenshots were regenerated with sample data; the alarm example remains an unsaved draft.

The earlier diagnostic run in `/tmp/casiosync-r4-browser-diagnose-css.log` reproduced `masterHidden:true` with `masterDisplay:"flex"`. This evidence explains why a CSS correction was needed and why checking the hidden attribute alone would have missed the defect.

Final Node32s/C3 builds, actual ELF panic/SNTP checks, image/partition/hash verification and downloaded-archive checks belong to the release owner's frozen-source evidence. The full suite must run after R4 publication under the user's release order, and its actual outcome must then be recorded.

The user's inherited BX time-sync result does not establish every optional setting on every watch. Separate settings groups can partially apply; stalled ATT work can abort a session at the bounded deadline. Settings readback confirms requested fields while the physical display remains unverified. The prior memory, lifetime, persistence, recovery and long-run-testing limits remain applicable.
